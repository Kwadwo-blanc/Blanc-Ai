# LLM From Scratch

A team project to build and train a small-scale language model from scratch,
using Python, PyTorch, and free GPU resources (Google Colab / Kaggle).

This repo has two parts:
1. **The from-scratch LLM** (the 9-phase roadmap below) -- the core
   learning exercise: build and train a small transformer from first
   principles.
2. **The medical Q&A module** (see its own section further down) -- a
   separate, retrieval-based tool that answers questions using your own
   PDF reference documents. It does NOT use the from-scratch model --
   that model is far too small to recall facts reliably, and medical
   information needs to be accurate, not just fluent-sounding. Instead
   this module searches your PDFs directly and returns real passages,
   so it can't hallucinate a fact that isn't in your source material.

## Phase 2 instructions (dataset collection & preparation)

1. Pull the latest from the repo (so you have `src/download_data.py` and
   `src/prepare_data.py`).
2. Download the starter dataset:
   ```
   python src/download_data.py
   ```
   This pulls the "Tiny Shakespeare" corpus into `data/raw/input.txt` --
   a small, clean public-domain text used to get the full pipeline
   working end-to-end before you plug in your own data.
3. Clean and split it into train/validation sets:
   ```
   python src/prepare_data.py
   ```
   This prints basic stats (character count, word count, vocab size)
   and writes `data/processed/train.txt` and `data/processed/val.txt`.
4. One person (or pair) should also start scouting a **custom dataset**
   for the real/final model -- something more meaningful than Shakespeare
   (e.g. news articles, a specific book, a domain you care about). Drop
   candidate `.txt` files in `data/raw/` as you find them; we'll decide
   together which one to train on for real once Phase 3 (tokenizer) is
   working.
5. Everyone runs steps 2-3 locally and confirms they see the same stats
   output in the team chat.

Phase 2 is complete once that's confirmed by everyone.

## Phase 3 instructions (tokenizer)

1. Pull the latest from the repo (so you have `src/tokenizer.py`).
2. Make sure `data/processed/train.txt` and `val.txt` exist (from Phase 2).
3. Run:
   ```
   python src/tokenizer.py
   ```
   This builds a character-level vocabulary from your dataset, encodes
   the train/val text into integer tensors, and saves:
   - `data/processed/train.pt` / `val.pt` -- the encoded data the model
     will actually train on
   - `data/processed/meta.json` -- the vocabulary (character <-> integer
     mappings) and vocab size, which Phase 4's model needs to know its
     input/output size
4. Check the printed stats -- vocab size, token counts, and the
   encode/decode sanity check (`'Hello' -> 'Hello'`). If the sanity
   check doesn't match, something's wrong with the data; flag it in
   the team chat.
5. Everyone runs this and confirms the same vocab size in the team chat
   (it should match everyone else's since you're all using the same
   `data/processed/train.txt` + `val.txt`).

**Things to understand for this phase (quick primer):** a tokenizer
maps text to numbers and back. Char-level (what we're using) is the
simplest -- one integer per character, small vocab, longer sequences.
Word-level or subword/BPE tokenizers (like `tiktoken`) use fewer,
longer tokens and are closer to what real LLMs use, at the cost of
more complexity. We're keeping it simple for now; this can be swapped
later if the team wants a more "production" feel for the final model.

Phase 3 is complete once everyone's vocab size matches.

## Phase 4 instructions (model architecture)

1. Pull the latest from the repo (so you have `src/model.py`).
2. Make sure `data/processed/meta.json` exists (from Phase 3).
3. Run:
   ```
   python src/model.py
   ```
   This builds the model (no training yet) and prints its architecture:
   vocab size, context length, embedding size, number of attention
   heads/layers, and total parameter count (should be a couple million
   -- small on purpose so it trains fast). It then runs one forward pass
   on random fake data as a sanity check -- the loss printed should be
   close to `ln(vocab_size)`, which is what a totally untrained model
   should produce by chance.
4. Everyone runs this and confirms the same parameter count and a
   sanity-check loss near the expected value.

**Things to understand for this phase (quick primer):** `src/model.py`
implements a decoder-only transformer -- the same family as GPT:
- **Token + position embeddings** turn each input token ID into a
  vector, and add information about *where* it is in the sequence.
- **Self-attention** (`CausalSelfAttention`) lets each position look
  back at earlier positions and decide which ones matter for predicting
  what comes next. "Causal" means it can't peek ahead -- essential for
  generating text left to right.
- **Feedforward layers** process each position's information further.
- These are stacked into **blocks** (`n_layer` of them), each wrapped
  in residual connections and layer norm for stable training.
- The **config** (`n_embd`, `n_head`, `n_layer`, `block_size`) controls
  model size vs. speed. Current defaults (~2.7M params) are tuned to
  train in minutes on a free Colab/Kaggle GPU. We can scale these up
  later once the pipeline is proven to work.

No new installs needed -- just `torch`, already in `requirements.txt`.

Phase 4 is complete once everyone confirms the same architecture printout.

## Phase 5 instructions (training loop & infrastructure)

1. Pull the latest from the repo (so you have `src/train.py`).
2. **Everyone** runs a quick local smoke test first, just to confirm the
   script works end-to-end:
   - Open `src/train.py` and temporarily change `MAX_ITERS = 3000` to
     `MAX_ITERS = 50`
   - Run `python src/train.py` -- on a laptop CPU this should finish in
     under a minute and print a few loss lines plus a saved checkpoint.
     Don't worry about the loss going down much; this is just confirming
     nothing crashes.
   - Revert the `MAX_ITERS` change afterward (don't commit it).
3. **One real training run as a team**, not 8 separate ones -- running
   the full thing 8 times burns everyone's free GPU quota for no
   benefit, and you want one shared checkpoint to move forward with,
   not 8 different models. Pick one or two people to:
   - Open `src/train.py` in a Colab or Kaggle notebook (GPU runtime on)
   - Run it with the default `MAX_ITERS = 3000` -- should take a few
     minutes on a free T4 GPU
   - Watch train/val loss print every 250 steps
   - Share the resulting `checkpoints/model.pt` file with the team
     (e.g. upload it to the repo via Git LFS, or drop it in shared
     Drive/WhatsApp if it's small -- it's ~15-20MB for this model size)
4. Everyone else reviews the loss curve shared in the team chat: train
   loss should steadily fall; val loss should fall too but may lag
   slightly behind train loss -- that gap is normal and only a problem
   if val loss starts *rising* while train loss keeps falling
   (overfitting).

**Things to understand for this phase (quick primer):**
- **Batching**: instead of training on one example at a time, we sample
  a batch of random chunks from the dataset at once -- faster and gives
  more stable gradient updates.
- **Forward pass -> loss -> backward pass -> optimizer step**: the model
  predicts next-tokens (forward), we measure how wrong it was (loss),
  compute how to adjust every parameter to reduce that error
  (backward/backpropagation), then actually adjust them (optimizer
  step, using AdamW here -- a standard, reliable optimizer).
- **Train vs. val loss**: val data is never trained on, so val loss
  tells you how well the model generalizes vs. just memorizing.
- **Checkpointing**: periodically saving model weights to disk so
  training can be resumed, or the model used later, without starting
  over.

No new installs needed -- just `torch`, already in `requirements.txt`.

Phase 5 is complete now that the team has one shared trained checkpoint
with a sensible loss curve.

## Phase 6 instructions (training & monitoring)

1. Pull the latest from the repo (so you have `src/generate.py`).
2. Make sure `checkpoints/model.pt` is in your local `checkpoints/`
   folder -- either from your own training run, or the file shared by
   whoever ran Phase 5's real training. Also make sure
   `data/processed/meta.json` exists (from Phase 3).
3. Run:
   ```
   python src/generate.py
   ```
   This loads the trained model, feeds it the starting text `"ROMEO:"`,
   and generates 300 more characters.
4. Open `src/generate.py` and try changing the `PROMPT` variable at the
   top to different starting text, then re-run. Also try changing
   `TEMPERATURE` (e.g. 0.5 for safer/more repetitive output, 1.2 for
   wilder output) to see how it changes things.
5. Share your favorite/funniest generated outputs in the team chat.

**Set expectations honestly:** with ~2.7M parameters trained for 3000
steps on ~1MB of text, this will NOT produce fully coherent Shakespeare.
What you're looking for is evidence the pipeline actually works: made-up
character names in the right format ("SOMENAME:"), real English words
appearing, roughly correct punctuation and line breaks, Shakespeare-ish
vocabulary. That's the architecture and training loop proving themselves
end to end -- which is the actual point of this phase, not literary
quality. A bigger model trained longer (or fine-tuned in Phase 8) would
read better.

**Things to understand for this phase (quick primer):**
- **Generation is autoregressive**: the model predicts one next character
  at a time, appends it, and feeds the whole thing back in to predict
  the next one -- repeat until you hit `MAX_NEW_TOKENS`.
- **Temperature** controls randomness in that prediction: low temperature
  makes the model always pick its most confident guess (safe, repetitive);
  high temperature flattens the odds so less-likely characters get picked
  more often (varied, but more likely to go off the rails).
- This step is "monitoring" in the sense that reading the actual output
  is how you sanity-check a model beyond just watching the loss number
  go down -- a low loss doesn't always mean the output looks sensible.

No new installs needed -- just `torch`, already in `requirements.txt`.

Phase 6 is complete once everyone's tried a few prompts and shared results.

## Phase 7 instructions (evaluation & testing)

1. Pull the latest from the repo (so you have `src/evaluate.py`).
2. Make sure `checkpoints/model.pt`, `data/processed/meta.json`, and
   `data/processed/train.pt`/`val.pt` are all present locally.
3. Run:
   ```
   python src/evaluate.py
   ```
   This:
   - Computes **perplexity** on train and val sets, averaged over 100
     batches each (far more stable than the quick checks during Phase 5
     training)
   - Prints the train/val gap with a verdict on whether the model looks
     like it's overfitting, underfitting, or generalizing reasonably
   - Generates text for 4 fixed prompts (`"ROMEO:"`, `"JULIET:"`,
     `"To be, or"`, `"The king"`) and saves everything to
     `eval_results.txt`
4. Share your `eval_results.txt` in the team chat. Since everyone is
   likely evaluating the **same shared checkpoint** from Phase 5, your
   numbers should match (small variation is normal -- the eval batches
   are randomly sampled each run). If numbers differ a lot between
   teammates, check you're all pointed at the same `checkpoints/model.pt`.
5. As a team, discuss and decide: is the pipeline solid enough to now
   train on a **real/custom dataset** (the one scouted back in Phase 2),
   or should hyperparameters be tuned first (bigger model, more
   iterations, different learning rate)? This decision sets up Phase 8.

**Things to understand for this phase (quick primer):**
- **Perplexity** is `e^(average loss)` -- it answers "roughly how many
  equally-likely next-characters was the model choosing between?" Lower
  is better. A perplexity near the vocab size (~65) means the model is
  basically guessing randomly; a working trained model should be well
  below that.
- **The train/val gap** is the real overfitting check, more reliable
  than eyeballing a single loss curve: if val loss is meaningfully
  *higher* than train loss, the model has started memorizing the
  training text rather than learning general patterns.
- **Why fixed prompts matter**: Phase 6 let everyone type random
  prompts, which makes outputs hard to compare. A fixed battery means
  everyone's `eval_results.txt` is testing the exact same thing, so
  differences in output reflect differences in the model/checkpoint,
  not differences in what was typed.

No new installs needed -- just `torch`, already in `requirements.txt`.

Phase 7 is complete -- results came back solid: train perplexity 3.98,

memorizing), and generated text hitting every mark expected at this

### Update: first run overfit -- `train.py` and `model.py` fixed

The first training run on this dataset came back overfit: train
perplexity 1.77, val perplexity 17.98, a gap of 2.32 (vs. the healthy
0.21 from the Shakespeare run) -- the model had essentially started
memorizing the training text instead of learning generalizable
patterns, which tracks with this dataset being ~10x smaller.

This also exposed a real bug: `train.py` was saving a checkpoint every
250 steps, but always to the same file path -- so the final saved
checkpoint was whatever the *last* step produced (the most overfit
point), with no way to recover an earlier, better one. That's fixed
now: `train.py` only saves when val loss improves on the best seen so
far, so `checkpoints/model.pt` always ends up holding the
best-generalizing version from that run, regardless of how long
training continues past that point. `model.py`'s dropout also went up
from 0.1 to 0.2 for extra regularization on small datasets.

**You'll need to retrain once more** with these fixes:
```
python src/train.py
```
on Colab/Kaggle as before. Then re-run `generate.py` and `evaluate.py`.
Expect the gap to shrink substantially; it may not fully match
Shakespeare's 0.21 given the dataset size difference, but it should be
well below 2.32.

## Medical Q&A module (retrieval-based, separate from the LLM phases)

**Why this isn't "train the LLM on medical PDFs":** the from-scratch
model is a character-level transformer trained on a few MB of text --
it predicts plausible-looking next characters, it does not reliably
recall facts. Trained on medical text, it would produce fluent
sentences that *sound* medical without necessarily being correct --
dangerous for something like dosage or treatment information. Real
medical Q&A needs to be accurate, not just fluent, so this module uses
a different, more appropriate technique: **retrieval** instead of
generation. It searches your actual PDF documents and returns the real
matching passage -- it cannot invent a fact that isn't in your source
material, because it never generates text at all, it only finds and
returns it.

**This is informational, not a real prescribing tool.** Every result
includes a disclaimer, and it should be presented in any demo/report
as "searches reference documents," not as "the AI decides your
medication."

### Setup instructions

1. Pull the latest from the repo (so you have `src/medical_extract.py`
   and `src/medical_search.py`).
2. Install the two new dependencies (already added to
   `requirements.txt`):
   ```
   pip install -r requirements.txt
   ```
3. Create a folder and drop your PDF files in:
   ```
   mkdir -p data/medical_pdfs
   ```
   (then copy your illness/symptom/treatment PDFs into that folder)
4. Extract and chunk the text:
   ```
   python src/medical_extract.py
   ```
   This reads every PDF, pulls out the text page by page, splits it
   into ~200-word overlapping chunks (small enough for precise search,
   with enough overlap that an answer near a chunk boundary isn't cut
   off awkwardly), and saves everything to `data/medical/chunks.json`
   along with which file and page each chunk came from.
5. Search it:
   ```
   python src/medical_search.py
   ```
   Drops you into an interactive prompt -- type a question like
   `symptoms of malaria` and it returns the top 3 matching passages
   with their source file, page number, and a relevance score. You can
   also run a one-off query without the interactive loop:
   ```
   python src/medical_search.py symptoms of malaria
   ```

### Things to understand for this module (quick primer)

- **TF-IDF + cosine similarity** is a classic information-retrieval
  technique: it scores how important each word is to a chunk (common
  words like "the" matter less, distinctive words like "malaria"
  matter more), turns your query into the same kind of score vector,
  and ranks chunks by how similar their vectors are. No training, no
  GPU, fully explainable -- good both practically and for writing up
  in a report.
- **Why chunking matters**: searching whole PDFs at once is too coarse
  (a 20-page document would match almost any query on the word
  "treatment" alone); searching whole pages can split a topic across a
  page boundary. ~200-word chunks are small enough for precise matches.
- **This can be upgraded later** to semantic/embedding-based search
  (which matches meaning, not just shared words -- so "cure" and
  "treatment" would match each other) if TF-IDF's keyword matching
  feels too literal once you're testing with real questions. Worth
  trying the simple version first and only upgrading if you hit its
  limits.

`data/medical/chunks.json` (the extracted/chunked output, ~1.8MB) is
ready to share with the team directly -- re-running
`medical_extract.py` isn't necessary unless the PDF set changes, since
the chunks file already has everything `medical_search.py` needs.

One cosmetic quirk to know about: a few chunks contain a reversed
sidebar label (e.g. "yrotaripseR" instead of "Respiratory") -- some of
these PDFs have a rotated category label running down the page edge,
and the extraction library reads it back-to-front. It doesn't affect
search quality (the real content extracts fine), just looks odd if you
spot it in a result. Not worth fixing unless it bothers you.
